# Metric reference

tokenscope emits eight OpenTelemetry metrics under the meter name
`tokenscope` (version `0.1.0`). All metrics use the `tokenscope.*`
namespace; tokenscope does **not** emit metrics under the
`gen_ai.*` namespace (rationale and equivalence table below).

## Common labels (Phase 7 update)

All per-session metrics carry the following labels in addition to any
metric-specific ones:

| Label | Source | Notes |
|---|---|---|
| `model` | `assistant.message.model` from the log | e.g. `claude-opus-4-7` |
| `session_id` | `sessionId` from the log | full UUID |
| `project` | encoded form of `cwd` (`/` and ` ` → `-`) | **unique** per host filesystem; same encoding Claude Code itself uses |
| `project_name` | last path segment of `cwd` | **friendly** display; can collide if two projects share a directory name |

`session_id` and `project` are unique identifiers; `project_name` is
the friendly display identifier. Dashboards show `project_name`, joins
and filters use `project`.

Both project labels are sanitized: control characters stripped, ≤ 64
chars (truncated with `...` ellipsis if longer). Missing `cwd` →
both labels = `"unknown"`.

## The eight metrics

### 1. `tokenscope.tokens.input`

| | |
|---|---|
| **Type** | `Counter<long>` |
| **Unit** | `{tokens}` |
| **Attributes** | `model`, `session_id` |
| **Emission** | Once per recorded request, when `input_tokens > 0` |
| **Source** | `assistant.message.usage.input_tokens` |

Non-cached input tokens billed at the full input rate. Excludes
tokens served from cache (those go on `tokens.cache_read`) and
tokens being seeded into cache (those go on `tokens.cache_write`).

### 2. `tokenscope.tokens.output`

| | |
|---|---|
| **Type** | `Counter<long>` |
| **Unit** | `{tokens}` |
| **Attributes** | `model`, `session_id` |
| **Emission** | Once per recorded request, when `output_tokens > 0` |
| **Source** | `assistant.message.usage.output_tokens` |

Output tokens generated by the model.

### 3. `tokenscope.tokens.cache_read`

| | |
|---|---|
| **Type** | `Counter<long>` |
| **Unit** | `{tokens}` |
| **Attributes** | `model`, `session_id` |
| **Emission** | Once per recorded request, when `cache_read_input_tokens > 0` |
| **Source** | `assistant.message.usage.cache_read_input_tokens` |

Cache hit tokens. **No `ttl` attribute** — the log does not record
the original TTL of the cached entry at read time, and Anthropic's
cache-read pricing is uniform (0.1× input) regardless of how the
entry was written.

### 4. `tokenscope.tokens.cache_write`

| | |
|---|---|
| **Type** | `Counter<long>` |
| **Unit** | `{tokens}` |
| **Attributes** | `model`, `session_id`, `ttl` ∈ `{5m, 1h}` |
| **Emission** | One measurement per TTL bucket, when that bucket's token count is > 0 |
| **Source** | `assistant.message.usage.cache_creation.ephemeral_{5m,1h}_input_tokens` |

Cache write tokens, split by TTL. A request that writes to both
5m and 1h caches emits two separate measurements for this counter.

### 5. `tokenscope.cost.usd`

| | |
|---|---|
| **Type** | `Counter<double>` |
| **Unit** | `USD` |
| **Attributes** | `model`, `session_id`, `component` ∈ `{input, output, cache_read, cache_write_5m, cache_write_1h}` |
| **Emission** | One measurement per component with `cost > 0` |
| **Source** | Computed by `TokenScope.Core.Costing.CostCalculator` from per-component tokens × per-MTok rates |

USD cost per component. The `component` attribute uses **flat
enumeration** (no separate `ttl` attribute) so Prometheus queries
like `sum by (component) (tokenscope_cost_usd_total)` work without
a join.

**Precision note.** The cost engine uses `decimal` internally; the
metric emits `double`. Conversion `(double)decimal` keeps ~15
significant digits — more than enough for USD costs at penny
precision up into the trillions. No precision-sensitive cost arrives
at the metric stage.

**Currency.** USD-only at v1. The pricing loader fails fast on any
non-USD `currency` in `pricing.json`. There is no FX conversion.
See [`pricing-model.md`](./pricing-model.md) for details.

### 6. `tokenscope.requests.total`

| | |
|---|---|
| **Type** | `Counter<long>` |
| **Unit** | `{requests}` |
| **Attributes** | `model`, `session_id` |
| **Emission** | One `+1` per call to `TokenScopeMetrics.RecordRequest` |
| **Source** | One unique `(sessionId, requestId)` after dedup |

Unique API request count. **Callers must deduplicate by
`(sessionId, requestId)` before calling `RecordRequest`**, because
the audit showed the same `requestId` can appear in multiple log
entries with byte-identical usage (up to 14× for one outlier).
Counting raw log events here would inflate request totals.

### 7. `tokenscope.cache.hit_ratio`

| | |
|---|---|
| **Type** | `ObservableGauge<double>` |
| **Unit** | `{ratio}` |
| **Attributes** | `session_id` |
| **Range** | `[0.0, 1.0]` |
| **Emission** | On scrape: one measurement per session whose cumulative `(cache_read + input) > 0` |
| **Source** | `CacheRatioTracker.Snapshot()` — rolling per-session totals |

Per-session rolling cache hit ratio: `cache_read / (cache_read + input)`.
Sessions whose cumulative cache_read + input is zero (e.g., a
session whose only events are `<synthetic>` placeholders) are
**omitted** — emitting `NaN` or `0` would either pollute aggregations
or misrepresent the data.

### 8. `tokenscope.sessions.active`

| | |
|---|---|
| **Type** | `ObservableGauge<long>` |
| **Unit** | `{sessions}` |
| **Attributes** | _(none)_ |
| **Emission** | One measurement on every scrape |
| **Source** | `SessionActivityTracker.CountActive(now, window)` |

Number of sessions whose most recent event timestamp is within the
**active-session window** (default 10 minutes; configurable via
`TokenScopeOtelOptions.ActiveSessionWindow`, eventually wired into
`tokenscope.yaml` in Phase 5).

The 10-minute default matches the 5-minute cache TTL window with
buffer — a session that has been silent for more than 10 minutes is
unlikely to benefit from its in-flight cache.

## Configuration

Production wiring uses the OTLP gRPC exporter via
`TokenScopeMeterProviderBuilderExtensions.AddTokenScopeMetricsWithOtlp`:

```csharp
using var provider = Sdk.CreateMeterProviderBuilder()
    .AddTokenScopeMetricsWithOtlp(new TokenScopeOtelOptions
    {
        OtlpEndpoint = "http://localhost:4317",        // default
        Protocol = OtlpExportProtocol.Grpc,            // default
        ActiveSessionWindow = TimeSpan.FromMinutes(10) // default
    })
    .Build();
```

For tests, use `AddTokenScopeMeter()` without an exporter and wire
an in-memory exporter or `MeterListener` to capture measurements
(see `tests/TokenScope.Otel.Tests/Metrics/MetricCapture.cs` for
the BCL `MeterListener` pattern).

## Estimated savings from caching

The "Saved by caching" stat on the unified `tokenscope` dashboard is
derived purely from existing metrics. No new instrument is required.

**Formula.** Cache reads cost 0.1× the base input rate (per Anthropic).
For each cache-read token, the user would have paid 1.0× input rate
without caching. Savings per token = 0.9× input rate. Expressed in
terms of the metrics we already emit:

```
savings_usd = Σ (cache_read_tokens × input_rate × 0.9)
            = (cost_cache_read_actual ÷ 0.1) − cost_cache_read_actual
            = 9 × cost_cache_read_actual
```

So:
```promql
sum(tokenscope_cost_usd_total{component="cache_read"}) * 9
```

This is exact for each Anthropic model in the pricing table: cache reads
are uniformly priced at 0.1× the model's base input rate, so the 9×
multiplier applies regardless of model mix.

Read the value as **"what you would have paid if cache hits had been
billed at full input rate, minus what you actually paid."** It's the
delta, not the would-have-been total.

## Dedup invariant

The dedup-by-`(sessionId, requestId)` rule from Phase 3 is the
caller's responsibility, not the metric layer's. Callers
(`TokenScope.Collector` in Phase 5+) must filter
`ParsedAssistantEvent.IsDuplicate == true` before invoking
`TokenScopeMetrics.RecordRequest`. The metric layer counts every
call as one request; duplicates would inflate
`tokenscope.requests.total` and double-count tokens / cost.

## Relationship to OTel `gen_ai.*` semantic conventions

OpenTelemetry has `gen_ai.client.*` semantic conventions for
applications that **call** an LLM. tokenscope is one layer up:
it observes such an application (Claude Code) by parsing its
logs after the fact. The semantic conventions assume request-level
context (operation name, response model, finish reason) that
post-hoc log analysis doesn't always have.

tokenscope therefore emits everything in the `tokenscope.*`
namespace. Dashboards built against `gen_ai.*` conventions can be
ported by relabel rules in Prometheus config rather than tokenscope
doubling its instrument count.

Approximate equivalences:

| `gen_ai.*` semantic convention | Closest tokenscope metric | Notes |
|---|---|---|
| `gen_ai.client.token.usage` (Counter, `{token}`, attr `gen_ai.token.type ∈ {input, output, ...}`) | `tokenscope.tokens.input` / `tokens.output` / `tokens.cache_read` / `tokens.cache_write` | tokenscope splits across four instruments instead of one; cache write/read are not in the `gen_ai` spec |
| `gen_ai.client.operation.duration` (Histogram, `s`) | _(none — not in tokenscope at v1)_ | Claude Code logs don't carry per-request duration. Could be derived from event-timestamp deltas in a future phase. |
| `gen_ai.client.token.usage` attribute `gen_ai.request.model` | tokenscope `model` attribute | Same intent, different attribute key |
| `gen_ai.client.token.usage` attribute `gen_ai.system` | _(implicit: tokenscope is Anthropic-only)_ | tokenscope sets no such attribute because every event is from Claude |

If you want a dashboard or alert query to target the `gen_ai.*`
shape, the easiest path is a Prometheus relabel:

```yaml
metric_relabel_configs:
  - source_labels: [__name__]
    regex: 'tokenscope_tokens_(input|output|cache_read|cache_write)_total'
    replacement: 'gen_ai_client_token_usage_total'
    target_label: __name__
  - source_labels: [model]
    target_label: gen_ai_request_model
```

## What is **not** emitted

| Field present in the log | Why we don't emit it as a metric |
|---|---|
| `service_tier` | Always `"standard"` in observed logs; `"batch"` would mean 0.5× cost, but the cost engine doesn't apply that modifier yet (Phase 6+). The field is captured on `ParsedAssistantEvent` for when it does. |
| `inference_geo` | Same story: a `"us"` value would apply a 1.1× premium, but the cost engine doesn't apply modifiers yet. |
| `speed` | Same story: a `"fast"` value would apply a 6× premium (fast mode). |
| `server_tool_use` (web_search_requests, web_fetch_requests) | Server-tool charges are flat-fee per use (e.g. $10/1000 web searches). Not a token-counter concern; future as a separate metric if/when relevant. |
| `iterations` | Redundant with top-level `usage` (sums to the same totals in observed data). Diagnostic-only. |
| `diagnostics` | Diagnostic metadata, no cost effect. |
| Per-request duration | Not present in the log (see `gen_ai` table above). |

These deliberate omissions document scope; revisit if a downstream
need emerges.
